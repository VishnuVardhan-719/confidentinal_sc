## Application contract

New modules are under `src/lib/notifications/`; all user routes use the existing bearer-session helper and user JWT/RLS. `await connection()` precedes GET processing; no route exports `dynamic`. Existing ops/contact routes were not recreated.

| HTTP | Body/query and result |
|---|---|
| `GET /api/notifications` | 20 rows ordered `(created_at DESC,id DESC)`; optional **paired** `before` ISO timestamp and `beforeId` UUID; `{notifications,nextCursor}` |
| `GET /api/notifications/unread-count` | `{count}`; count-only SELECT |
| `POST /api/notifications/read` | Exactly `{ids: uuid[1..100]}` or `{before: ISO timestamp}`; `{count}` |
| `GET /api/notifications/preferences` | `{preferences}`; absent channel/topic rows mean OFF |
| `PUT /api/notifications/preferences` | `{channel,topic,enabled,noticeVersion,expectedVersion}`; first expected version is 0; `{version}` |
| `GET /api/admin/notifications/failures` | `limit` 1–100, default 50; optional `after` UUID; `{failures}` without recipient/booking/destination |
| `GET` / `POST /api/internal/notifications/dispatch` | Constant-time bearer CRON_SECRET authentication; counts only; no scheduler configured |

The four user RPCs are **not keyed in the published SQL contract**. No Idempotency-Key or invented RPC parameter was added. Feature-unavailable maps to 404; suspension/transport/config failures to sanitized 503; scoped denial to 404; version conflicts to 409; invalid input to 422; limits to 429. Responses are private/no-store. Strict request and response validation prevents authority injection and accidental additional database fields.

Dispatcher claims at most 50 per channel and starts that bounded batch concurrently, with a 10-second timeout per send. It awaits all completion attempts before returning or reporting failure. No destination, rendered body or raw vendor/database error is logged. The worker client is server-only and explicitly uses `notify_worker`; that schema is added to local `supabase/config.toml`. A hosted project's exposed-schema setting must match before any future dispatcher activation.

`.env.example` documents default-false `FEATURE_NOTIFY_SMS`, `FEATURE_NOTIFY_EMAIL`, `FEATURE_NOTIFY_WHATSAPP`, `NOTIFY_*_ADAPTER=log`, `APP_ORIGIN` and `CRON_SECRET`. No `.env` was read or written. Server env validation rejects enabled channels with unreviewed translations/unknown or absent adapters, and rejects WhatsApp automation unconditionally. All Telugu/Hindi entries are English placeholders with `reviewed:false`; inbox falls back to English. External sending cannot be activated with those placeholders. Future authenticated locale dashboards must exist at the documented own-origin paths before external activation.
