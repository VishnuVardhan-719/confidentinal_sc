## Implementation and boundaries

- `FEATURE_PAY_AFTER` enables `payAfter` only for the exact string `true`; default OFF. Every adapter returns 404 `feature_unavailable` before authentication, body consumption or RPC access when closed.
- Fourteen fixed-operation adapters use the existing bearer session and private/no-store responses. Admin and collector authorization, AAL2, conflict exclusions, verified assignments, remaining balances, window checks, versions, paid-state gates and durable keyed replay must be enforced by the future SQL functions. No application-side role or capability substitute is introduced.
- Each RPC input has a strict Zod schema, including direct service calls. Claims take positive decimal-string paise with at most 15 digits, cash with no reference, or UPI with exactly 12 ASCII digits. No amount is parsed through `Number`. RPC money results become strings; unsafe numeric money is rejected.
- Mutations require a UUID `Idempotency-Key`. Bodies use `expectedPaymentVersion`, `reasonCode`, and the command-specific `decision`, `resolutionCode` or `targetState`. Reports use `{ amountPaise, method, reference? }`; superseding adds the claim fields to a decision body. No unrecognized fields are accepted.
- Read pagination uses `limit` (default 25, maximum 100), `afterId`, and for finance lists the paired `afterReportedAt`. Duplicate/unknown query parameters and incomplete finance cursors are rejected.
- Report/exception/supersede responses are `{ id }`; summary `{ payment }`; intake status `{ intake }`; provider list `{ payments }`; finance queue `{ collections }`; exception queue `{ exceptions }`; other commands `{ result: null }` under the void-return assumption below. None fabricates a payment success or a paid state.
- Errors: no session/authentication SQLSTATEs -> 401; `42501`/`P0002` -> scoped 404; closed DB gate -> 404; state/version/idempotency/over-collection conflicts -> 409; other input violations -> 422; limits -> 429; unavailable database/transport -> sanitized 503. No retries, upstream details or sensitive logging.
- The nested void URL validates both booking and collection UUIDs. Its design RPC accepts only the collection UUID, which is the authorization target; the booking URL component is not an additional SQL predicate.

## Exact RPC contract for the SQL author

All functions are in `public`, called with the authenticated request's client. Paise is PostgreSQL `bigint` transported as a JSON decimal string. Nullable arguments are sent explicitly as `null`.

```sql
report_collection(p_booking_id uuid, p_amount_paise bigint, p_method text, p_reference text, p_request_key uuid) returns uuid
report_collection_exception(p_booking_id uuid, p_amount_paise bigint, p_method text, p_reference text, p_request_key uuid) returns uuid
review_collection_intake(p_intake_id uuid, p_decision text, p_reason_code text, p_expected_payment_version integer, p_request_key uuid) returns void
void_collection(p_collection_id uuid, p_expected_payment_version integer, p_reason_code text, p_request_key uuid) returns void
reconcile_collection(p_collection_id uuid, p_decision text, p_reason_code text, p_expected_payment_version integer, p_request_key uuid) returns void
supersede_collection(p_collection_id uuid, p_amount_paise bigint, p_method text, p_reference text, p_reason_code text, p_expected_payment_version integer, p_request_key uuid) returns uuid
dispute_payment(p_booking_id uuid, p_reason_code text, p_expected_payment_version integer, p_request_key uuid) returns void
resolve_dispute(p_payment_id uuid, p_resolution_code text, p_expected_payment_version integer, p_request_key uuid) returns void
override_payment(p_payment_id uuid, p_target_state text, p_reason_code text, p_expected_payment_version integer, p_request_key uuid) returns void
get_payment_summary(p_booking_id uuid) returns jsonb
get_collection_intake_status(p_intake_id uuid) returns jsonb
list_provider_payments(p_provider_id uuid, p_limit integer, p_after_id uuid) returns setof jsonb
list_payment_queue(p_limit integer, p_after_reported_at timestamptz, p_after_id uuid) returns setof jsonb
list_payment_exceptions(p_limit integer, p_after_reported_at timestamptz, p_after_id uuid) returns setof jsonb
```

Explicit assumptions where the design leaves the contract incomplete:

1. Commands with no documented return type use `void` (PostgREST `null`); intake status returns `{ id, status, reportedAt }` JSON. Queue/exception rows return JSON with string paise fields and the projections in section 7.
2. `list_payment_exceptions(...)` uses the finance queue's `p_limit`, `p_after_reported_at`, `p_after_id` signature and paired cursor, since section 7 says same pagination but omits its signature. SQL must settle which exception timestamp backs that alias.
3. Intake review reasons and dispute resolution codes reuse section 4.1's closed collection reasons: `amount_mismatch`, `not_received`, `duplicate`, `wrong_payee`, `correction`, `other`. The design requests closed lists without enumerating these two lists; reconcile with SQL before activation. Patient disputes use their separate exact section 7 list.
4. Override targets are `due`, `partially_paid`, `paid`, `disputed`, matching the seeded `admin_override` transitions; the DB paid gate and confirmed-collection checks still control the financial states.
